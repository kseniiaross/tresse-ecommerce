# Post-audit fixes — September 2026

## P1-07: Shipping/delivery emails were never sent, and the FAQ tracking link had nothing to point to

**What was broken:** `orders/emails.py` had `send_shipping_confirmation_email()`
and `send_delivered_email()`, and their templates already existed, but
neither function was ever called — there was no admin action and the
Stripe webhook never invoked them. `delivered_at` was only ever set by
hand, silently, in the Django admin, and `RequestReturnAPIView`'s return
window is computed from that field. The `Order` model also had no tracking
number field at all, so the FAQ's promised tracking link could never be
populated.

**Why it mattered:** Customers placed orders and never received a shipping
or delivery notification, even though the templates for both existed.
Staff had to remember to set `delivered_at` by hand with no reminder to do
so, silently starting the customer's return window, and there was nowhere
in the system to record a tracking number even if support wanted to share
one manually.

**Files changed:**
- `orders/models.py` — added `tracking_number` (`CharField`, blank),
  `tracking_carrier` (`CharField`, default `"USPS"`) and `shipped_at`
  (`DateTimeField`, nullable) to `Order`.
- `orders/migrations/0017_order_shipped_at_order_tracking_carrier_and_more.py`
  (new) — migration for the three fields above.
- `orders/admin.py` — added `tracking_number`, `tracking_carrier` and
  `shipped_at` to the "Shipping" fieldset (`shipped_at` read-only, set only
  by the new action) and `shipped_at` to `list_display` next to
  `delivered_at`. Added two admin actions: "Mark selected orders as
  shipped" (for each `status="paid"` order with a `tracking_number` and no
  `shipped_at`, sets `shipped_at` to now and sends
  `send_shipping_confirmation_email` with a tracking URL built from
  `tracking_carrier`) and "Mark selected orders as delivered" (for each
  order with `shipped_at` set and no `delivered_at`, sets `delivered_at` to
  now and sends `send_delivered_email`). Both actions update the DB inside
  `transaction.atomic()` per order, then send email afterwards, outside the
  transaction, so an SMTP failure cannot roll back the timestamp update;
  ineligible orders are skipped and counted, and a failed send is logged
  and counted, following the same pattern as `approve_return` and the
  reminder actions in `accounts/admin.py`.
- `orders/serializers.py` — added `tracking_number`, `tracking_carrier` and
  `shipped_at` to `OrderReadSerializer.Meta.fields` (already covered by
  `read_only_fields = fields`) so the frontend can display them.
- `orders/tests.py` — added `OrderAdminShippingActionsTestCase` covering
  both actions' happy path (email sent, timestamp set) and skip path
  (ineligible order left untouched, no email sent), mocking the email
  functions.

**How to verify:** Run `pytest orders`.

## P1-09: Order emails showed internal ID instead of public order number

**What was broken:** All five order email templates (`order_confirmation.txt`,
`order_canceled.txt`, `refund_initiated.txt`, `shipping_confirmation.txt`,
`delivered.txt`) rendered the order number in the email body as
`#{{ order.id }}` — the internal database primary key. The email subject
line, built by `_order_label()` in `orders/emails.py`, already used
`order.public_id` (e.g. `TR-20260813-K7M2QX`).

**Why it mattered:** A single email showed two different order numbers —
the subject said `TR-20260813-K7M2QX`, the body said `#42`. Customers quote
the number from the body when contacting support, but the Django admin
searches and lists orders by `public_id`, not by primary key, so support
could not find the order from the number the customer gave them.

**Files changed:**
- `templates/emails/orders/order_confirmation.txt`
- `templates/emails/orders/order_canceled.txt`
- `templates/emails/orders/refund_initiated.txt`
- `templates/emails/orders/shipping_confirmation.txt`
- `templates/emails/orders/delivered.txt`

Each now renders `{% if order.public_id %}{{ order.public_id }}{% else %}#{{ order.id }}{% endif %}`
instead of `#{{ order.id }}`, so the body matches the subject and falls
back to the primary key only if `public_id` is unset.

**How to verify:** Run `pytest orders` (covers template rendering smoke
tests in `orders/tests.py`). To check manually, render any of the five
templates with an order that has a `public_id` and confirm the body shows
the same `TR-...` value as the email subject.

## P1-08: Newsletter welcome email greeted subscribers with "Hi ,"

**What was broken:** `templates/emails/accounts/newsletter_welcome.txt`
started with `Hi {{ name }},`, but `newsletter/views.py` only passes
`email`, `source` and `brand` into the render context — no `name`. Django
silently renders a missing variable as an empty string, so the email began
"Hi ,". The bug was invisible in tests because every subscribe test in
`newsletter/tests.py` mocks `render_to_string`, so the real template was
never rendered. The `.txt` and `.html` versions of the same email also
differed in content: the `.html` version has no greeting and mentions
"limited releases", which the `.txt` version lacked.

**Why it mattered:** Every newsletter subscriber received a welcome email
with a visibly broken greeting ("Hi ,"), and the plain-text and HTML parts
of the same email read as different messages.

**Files changed:**
- `templates/emails/accounts/newsletter_welcome.txt` — removed the `Hi
  {{ name }},` greeting and aligned the wording with
  `newsletter_welcome.html` (no greeting, matching copy).
- `newsletter/tests.py` — added `NewsletterWelcomeTemplateRenderTestCase`,
  which renders both `newsletter_welcome.txt` and `newsletter_welcome.html`
  for real (no `render_to_string` mock) using the same context the view
  passes, and asserts the output contains no `"Hi ,"` and no unresolved
  `{{ ... }}` template variables.

**How to verify:** Run `pytest newsletter`.

## P0-05: Newsletter subscribe endpoint had no rate limiting and re-emailed active subscribers

**What was broken:** `SubscribeAPIView` (`newsletter/views.py`) was `AllowAny`
with no `throttle_classes` and no captcha, unlike `accounts` endpoints
(register, login, reset, restore), which apply both. It also sent the
welcome email on every POST, including repeat POSTs for a subscriber who
was already active, since the email send was unconditional on the create
path.

**Why it mattered:** A script could loop third-party email addresses
against the endpoint with no rate limit, and every POST — including
repeats for the same already-subscribed address — triggered a real email
from our domain to a real inbox. That produces spam complaints against
addresses that never opted in and risks suspension by our email provider.

**Files changed:**
- `newsletter/throttles.py` (new) — `NewsletterAnonThrottle(AnonRateThrottle)`
  with `scope = "newsletter_anon"`.
- `newsletter/views.py` — attached `throttle_classes = [NewsletterAnonThrottle]`
  to `SubscribeAPIView`; the welcome email is now sent only when the
  subscriber is newly `created`, or when an existing subscriber is
  reactivated from `is_active=False`. A repeat POST for an already-active
  subscriber returns 200 with `email_sent: False` and sends nothing.
- `tresse/settings.py` — added `"newsletter_anon": config("THROTTLE_NEWSLETTER_ANON", default="5/min")`
  to `DEFAULT_THROTTLE_RATES`, matching the `login`/`register`/`restore`/
  `stock_subscribe` pattern.
- `newsletter/tests.py` — extended `test_resubscribing_active_no_changes_returns_200`
  to assert `email_sent` is `False` and no email call is made; added
  `test_second_post_for_active_subscriber_does_not_send_email`, which POSTs
  twice for the same address and asserts the second POST does not render
  or send an email.

**How to verify:** Run `pytest newsletter`.

## P1-16: Cart, wishlist, and back-in-stock emails linked to the wrong domain

**What was broken:** `send_cart_reminder_email` and
`send_wishlist_reminder_email` (`products/emails.py`) defaulted their
`cart_url`/`wishlist_url` parameters to hardcoded
`https://www.tresseknitting.com/cart` and `/wishlist` URLs, and
`notify_when_back_in_stock` (`products/signals.py`) built its
`product_url` the same way. `tresseknitting.com` is a separate domain
used only for the support mailbox and currently serves a placeholder
"under construction" page; the live storefront is `tressehandmade.com`.

**Why it mattered:** A customer clicking the cart, wishlist, or
back-in-stock link in these emails landed on a placeholder page instead
of the shop, with no way to complete their purchase from the email.

**Files changed:**
- `products/emails.py` — `cart_url` and `wishlist_url` now default to
  `""` and are built from `settings.FRONTEND_URL.rstrip("/")` inside the
  function body when not supplied, matching the pattern used by
  `_support_context()` in `orders/emails.py`. Both parameters remain
  overridable by the caller.
- `products/signals.py` — `product_url` in `notify_when_back_in_stock`
  is now built from `settings.FRONTEND_URL.rstrip("/")` instead of the
  hardcoded `tresseknitting.com` domain.

`DEFAULT_FROM_EMAIL`, `SUPPORT_EMAIL`, and the `support@tresseknitting.com`
address were left untouched — the support mailbox stays on
`tresseknitting.com` deliberately.

**Remaining hardcoded `tresseknitting.com` references (not changed):**
- `orders/views_stripe.py:533` and `orders/views.py:318` — both fall back
  to `"https://www.tresseknitting.com"` in `getattr(settings,
  "FRONTEND_URL", "https://www.tresseknitting.com")` if `FRONTEND_URL`
  isn't set at all. Only a `getattr` default, not user-facing unless
  `FRONTEND_URL` is missing from settings.
- `accounts/tests.py` and `orders/tests.py` — test fixtures asserting
  against `tresseknitting.com` support/help/restore URLs.
- `.env` and `tresse/settings.py` — `DEFAULT_FROM_EMAIL` /
  `SUPPORT_EMAIL` on `support@tresseknitting.com`, which is correct and
  intentionally out of scope.

**How to verify:** Run `pytest products`.

## P1-16 (part 2): Stripe checkout success/cancel URLs fell back to the wrong domain

**What was broken:** `orders/views_stripe.py` and `orders/views.py` built
`frontend_url` (used for the Stripe checkout session's `success_url` and
`cancel_url`) with `getattr(settings, "FRONTEND_URL",
"https://www.tresseknitting.com")`. `FRONTEND_URL` is declared in
`tresse/settings.py` as `config("FRONTEND_URL")` with no default, so
Django won't start without it and the fallback was unreachable — but it
was still the wrong domain, same as the rest of P1-16.

**Why it mattered:** Dead code aside, if `FRONTEND_URL` were ever missing
a paying customer would be redirected from Stripe checkout to
`tresseknitting.com`'s placeholder page instead of the order
confirmation page.

**Files changed:**
- `orders/views_stripe.py` and `orders/views.py` — `frontend_url` is now
  `settings.FRONTEND_URL` directly; the `getattr` and its fallback string
  are gone.

**How to verify:** Run `pytest orders`.

## P1-18: `orders/views.py` had a dead second copy of the Stripe checkout/webhook code

**What was broken:** `orders/views.py` carried a full duplicate of
`create_checkout_session`, `stripe_webhook`, `_sync_refund_event`, and
every helper they used — roughly 700 lines identical to
`orders/views_stripe.py`. `orders/urls.py` only ever imported
`create_checkout_session` and `stripe_webhook` from `views_stripe`, and
only `MyOrdersAPIView`, `CancelOrderAPIView`, and `RequestReturnAPIView`
from `views`, and the test suite exclusively patches
`orders.views_stripe`. So the copy in `views.py` never ran in production
and never ran under test: a developer fixing a webhook bug could patch
`views.py`, watch the tests stay green (they never touch that file), and
ship no actual change. The P1-16 (part 2) fix had to be applied to both
files for exactly this reason.

**Why it mattered:** Dead code that looks alive is worse than no code —
it wastes the next bug fix and gives false confidence from a passing
test suite that didn't test what was changed.

**Files changed:**
- `orders/views.py` — deleted `create_checkout_session`, `stripe_webhook`,
  `_sync_refund_event`, and the helpers/imports/constants only they used
  (`_safe_decimal`, `_normalize_size_label`, `_metadata_is_true`,
  `_money_to_cents`, `_cents_to_money`, `_item_unit_price`,
  `_cart_has_custom_size`, `_cart_has_custom_length`,
  `_build_cart_signature`, `_user_has_paid_order`,
  `_extract_card_details_from_payment_intent`, `WELCOME_PROMO_CODE`,
  `POLICY_VERSION`, and the now-unused `hashlib`, `Decimal`,
  `ROUND_HALF_UP`, `Iterable`, `Cart`, `CartItem`, `get_user_model`,
  `csrf_exempt`, `api_view`, `permission_classes` imports). The file now
  holds only `MyOrdersAPIView`, `CancelOrderAPIView`,
  `RequestReturnAPIView`, and the constants/helpers those three actually
  use (`CUSTOM_SIZE_LABEL`, `CANCEL_WINDOW`, `RETURN_WINDOW`, `_safe_str`,
  `_build_items_payload`). `orders/views_stripe.py` is unchanged and
  remains the only Stripe checkout/webhook code path.

**How to verify:** Run `python manage.py check && pytest orders && ruff
check . && ruff format --check .`. Confirmed `orders/urls.py` still
resolves all five routes and nothing outside `views_stripe.py` imports
the deleted names.
