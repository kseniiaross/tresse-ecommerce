# Post-audit fixes — September 2026

## P1-07: Shipping/delivery emails were never sent, and the FAQ tracking link had nothing to point to

**What was broken:** `orders/emails.py` had `send_shipping_confirmation_email()`
and `send_delivered_email()`, and their templates already existed, but
neither function was ever called — there was no admin action and the
Stripe webhook never invoked them. `delivered_at` was only ever set by
hand, silently, in the Django admin, and `RequestReturnAPIView`'s return
window is computed from that field. The `Order` model also had no tracking
number field at all, so the FAQ's promised tracking link could never be
populated.

**Why it mattered:** Customers placed orders and never received a shipping
or delivery notification, even though the templates for both existed.
Staff had to remember to set `delivered_at` by hand with no reminder to do
so, silently starting the customer's return window, and there was nowhere
in the system to record a tracking number even if support wanted to share
one manually.

**Files changed:**
- `orders/models.py` — added `tracking_number` (`CharField`, blank),
  `tracking_carrier` (`CharField`, default `"USPS"`) and `shipped_at`
  (`DateTimeField`, nullable) to `Order`.
- `orders/migrations/0017_order_shipped_at_order_tracking_carrier_and_more.py`
  (new) — migration for the three fields above.
- `orders/admin.py` — added `tracking_number`, `tracking_carrier` and
  `shipped_at` to the "Shipping" fieldset (`shipped_at` read-only, set only
  by the new action) and `shipped_at` to `list_display` next to
  `delivered_at`. Added two admin actions: "Mark selected orders as
  shipped" (for each `status="paid"` order with a `tracking_number` and no
  `shipped_at`, sets `shipped_at` to now and sends
  `send_shipping_confirmation_email` with a tracking URL built from
  `tracking_carrier`) and "Mark selected orders as delivered" (for each
  order with `shipped_at` set and no `delivered_at`, sets `delivered_at` to
  now and sends `send_delivered_email`). Both actions update the DB inside
  `transaction.atomic()` per order, then send email afterwards, outside the
  transaction, so an SMTP failure cannot roll back the timestamp update;
  ineligible orders are skipped and counted, and a failed send is logged
  and counted, following the same pattern as `approve_return` and the
  reminder actions in `accounts/admin.py`.
- `orders/serializers.py` — added `tracking_number`, `tracking_carrier` and
  `shipped_at` to `OrderReadSerializer.Meta.fields` (already covered by
  `read_only_fields = fields`) so the frontend can display them.
- `orders/tests.py` — added `OrderAdminShippingActionsTestCase` covering
  both actions' happy path (email sent, timestamp set) and skip path
  (ineligible order left untouched, no email sent), mocking the email
  functions.

**How to verify:** Run `pytest orders`.

## P1-09: Order emails showed internal ID instead of public order number

**What was broken:** All five order email templates (`order_confirmation.txt`,
`order_canceled.txt`, `refund_initiated.txt`, `shipping_confirmation.txt`,
`delivered.txt`) rendered the order number in the email body as
`#{{ order.id }}` — the internal database primary key. The email subject
line, built by `_order_label()` in `orders/emails.py`, already used
`order.public_id` (e.g. `TR-20260813-K7M2QX`).

**Why it mattered:** A single email showed two different order numbers —
the subject said `TR-20260813-K7M2QX`, the body said `#42`. Customers quote
the number from the body when contacting support, but the Django admin
searches and lists orders by `public_id`, not by primary key, so support
could not find the order from the number the customer gave them.

**Files changed:**
- `templates/emails/orders/order_confirmation.txt`
- `templates/emails/orders/order_canceled.txt`
- `templates/emails/orders/refund_initiated.txt`
- `templates/emails/orders/shipping_confirmation.txt`
- `templates/emails/orders/delivered.txt`

Each now renders `{% if order.public_id %}{{ order.public_id }}{% else %}#{{ order.id }}{% endif %}`
instead of `#{{ order.id }}`, so the body matches the subject and falls
back to the primary key only if `public_id` is unset.

**How to verify:** Run `pytest orders` (covers template rendering smoke
tests in `orders/tests.py`). To check manually, render any of the five
templates with an order that has a `public_id` and confirm the body shows
the same `TR-...` value as the email subject.

## P0-05: Newsletter subscribe endpoint had no rate limiting and re-emailed active subscribers

**What was broken:** `SubscribeAPIView` (`newsletter/views.py`) was `AllowAny`
with no `throttle_classes` and no captcha, unlike `accounts` endpoints
(register, login, reset, restore), which apply both. It also sent the
welcome email on every POST, including repeat POSTs for a subscriber who
was already active, since the email send was unconditional on the create
path.

**Why it mattered:** A script could loop third-party email addresses
against the endpoint with no rate limit, and every POST — including
repeats for the same already-subscribed address — triggered a real email
from our domain to a real inbox. That produces spam complaints against
addresses that never opted in and risks suspension by our email provider.

**Files changed:**
- `newsletter/throttles.py` (new) — `NewsletterAnonThrottle(AnonRateThrottle)`
  with `scope = "newsletter_anon"`.
- `newsletter/views.py` — attached `throttle_classes = [NewsletterAnonThrottle]`
  to `SubscribeAPIView`; the welcome email is now sent only when the
  subscriber is newly `created`, or when an existing subscriber is
  reactivated from `is_active=False`. A repeat POST for an already-active
  subscriber returns 200 with `email_sent: False` and sends nothing.
- `tresse/settings.py` — added `"newsletter_anon": config("THROTTLE_NEWSLETTER_ANON", default="5/min")`
  to `DEFAULT_THROTTLE_RATES`, matching the `login`/`register`/`restore`/
  `stock_subscribe` pattern.
- `newsletter/tests.py` — extended `test_resubscribing_active_no_changes_returns_200`
  to assert `email_sent` is `False` and no email call is made; added
  `test_second_post_for_active_subscriber_does_not_send_email`, which POSTs
  twice for the same address and asserts the second POST does not render
  or send an email.

**How to verify:** Run `pytest newsletter`.

## P0-01: Back-in-stock signal handler was never connected — no restock email was ever sent

**What was broken:** `products/signals.py` defines `notify_when_back_in_stock`
as a `post_save` receiver on `ProductSize`, but `ProductsConfig.ready()`
(`products/apps.py`) contained only `pass` — nothing ever imported

the tests proved the handler body worked, not that anything ever invoked
it.

**Why it mattered:** The entire back-in-stock notification feature was
dead: customers who signed up to be notified when a product restocked
never received anything, silently, with a fully green test suite masking
it.

**Files changed:**
- `products/apps.py` — `ready()` now imports `products.signals` so the
  `@receiver` decorator executes and the handler is connected.

**How to verify:** Run `pytest products`. See also [[P0-02]] below — the
handler could not be connected as-is; it had to be fixed first.

## P0-02: Back-in-stock handler had no restock guard and would have emailed subscribers on every purchase

**What was broken:** `notify_when_back_in_stock`'s only guard was `if
instance.quantity <= 0: return` — no check that the quantity actually
crossed from zero to positive. Connecting it as-is (see [[P0-01]]) would
have fired on any `post_save` with a positive quantity: an admin edit, a
new size being added with stock already set, and critically the
`product_size.save(update_fields=["quantity"])` in the Stripe webhook
(`orders/views_stripe.py`) where stock is *decremented* after a purchase.
A customer buying the last-but-one unit (stock 5 → 4) would have caused
every pending subscriber to receive a "back in stock" email. The send was
also synchronous and ran inside the order-creation transaction, so a
rollback of that transaction would still have left the emails sent, and
failures were swallowed with `print("RESTOCK EMAIL ERROR:", exc)` instead
of being logged.

**Why it mattered:** Turning the feature on without this guard would have
been worse than leaving it off — it would have spammed subscribers on
routine purchases instead of restocks, from inside a code path (the Stripe
webhook) where an unhandled exception or slow SMTP call could jeopardize
order creation itself.

**Files changed:**
- `products/models.py` — `ProductSize` now tracks the quantity it started
  with in `self.__original_quantity`, set in `__init__` for
  newly-constructed instances and overwritten with the real stored value
  by an overridden `from_db()` when the instance is loaded from the
  database.
- `products/signals.py` — `notify_when_back_in_stock` now reads that
  previous quantity (under its mangled name, since the tracking attribute
  belongs to `ProductSize`, not this function) and returns unless the
  save is a genuine zero-to-positive transition. Sending is now deferred
  to `transaction.on_commit`, the same pattern
  `orders/views_stripe.py` uses for the order confirmation email, so a
  rolled-back transaction sends nothing. `print("RESTOCK EMAIL
  ERROR:", exc)` is replaced with `logger.exception(...)`.
- `products/tests.py` — `StockSignalTestCase`'s existing tests now wrap
  their saves in `self.captureOnCommitCallbacks(execute=True)` (required
  once sending moved to `on_commit`, since `TestCase` never actually
  commits). Added three tests covering the transition explicitly: 5 → 4
  sends nothing, 0 → 3 sends, and 3 → 5 sends nothing.

**How to verify:** Run `pytest products`.

## P0-06: Newsletter had no unsubscribe path (backend)

**What was broken:** `NewsletterSubscriber.is_active` existed but nothing
in the app could set it to `False` — `newsletter/urls.py` exposed only
`subscribe/`, and the flag was only editable by hand in the admin.
Neither welcome template (`newsletter_welcome.txt` / `.html`) contained
an unsubscribe link.

**Why it mattered:** For commercial email this breaks both CAN-SPAM and
GDPR/ePrivacy — a working one-click unsubscribe is mandatory in every
message, and there was no way for a subscriber to opt out short of asking
someone to edit the database.

**Files changed:**
- `newsletter/tokens.py` (new) — `make_unsubscribe_token`/
  `read_unsubscribe_token` sign and verify the subscriber's *email* (not a
  raw id) via `django.core.signing`, so a token can't be forged or
  guessed to unsubscribe someone else. `read_unsubscribe_token` raises
  `signing.SignatureExpired` for an expired token and `signing.BadSignature`
  for a tampered/malformed one. `build_unsubscribe_url(email)` builds the
  frontend link from `settings.FRONTEND_URL`, the same way
  `products/emails.py` builds the cart/product links.
- `newsletter/views.py` — new `UnsubscribeAPIView` (`AllowAny`,
  `NewsletterAnonThrottle`, same DB-error handling shape as
  `SubscribeAPIView`): a valid token sets `is_active=False` and returns
  200; an invalid or expired token returns 400 with a `detail` message;
  an already-inactive subscriber returns 200 with no write. The welcome
  email context built in `SubscribeAPIView.post` now includes
  `unsubscribe_url`.
- `newsletter/urls.py` — added
  `unsubscribe/<str:token>/` → `UnsubscribeAPIView`
  (`newsletter_unsubscribe`). The token in the URL points at the
  *frontend* route `/newsletter/unsubscribe/<token>/`, which is expected
  to call this API.
- `templates/emails/accounts/newsletter_welcome.txt` and `.html` — both
  now render `{{ unsubscribe_url }}` as a visible unsubscribe link.
- `newsletter/tests.py` — added `UnsubscribeAPITestCase`: a valid token
  deactivates the subscriber, a tampered token leaves it active and
  returns 400, an expired token returns 400, an already-inactive
  subscriber stays inactive with a 200, and a token for an unknown email
  returns 400. Extended `NewsletterWelcomeTemplateRenderTestCase`'s real
  context with `unsubscribe_url` and added a test per template asserting
  the link is present in the rendered output.

**How to verify:** Run `pytest newsletter`.

## P1-04: Profile form never saved first name, last name, address line 1 or postal code

**What was broken:** `ProfileSerializer` and `ProfileAPIView`
(`accounts/serializers.py`, `accounts/views.py`) used camelCase keys
(`firstName`, `lastName`, `addressLine1`, `postalCode`), but the frontend
(`ProfileUpdatePayload` / `mapFormToApi` in the Dashboard) sends, and
`mapApiToForm` reads, snake_case (`first_name`, `last_name`,
`address_line1`, `postal_code`). The view applies only what is in
`serializer.validated_data`, and DRF silently drops unknown keys, so a PUT
returned 200 and changed nothing for those four fields. Only the
single-word fields (`email`, `apartment`, `city`, `state`, `country`) were
saved, because their names are the same in both cases. The GET response
had the same mismatch: it returned the four fields under camelCase keys
the frontend never reads, so they always came back empty.

**Why it mattered to the customer:** Saving the profile showed "Saved."
and kept a copy in localStorage, so the form looked correct in that
browser. The server never stored the name, street address or postal code,
so they were lost on another device or after clearing site data, and the
Dashboard never pre-filled them from the server.

**Files changed:**
- `accounts/serializers.py` — `ProfileSerializer` fields renamed to
  `first_name`, `last_name`, `address_line1`, `postal_code`.
- `accounts/views.py` — `ProfileAPIView` GET, the PUT field handling and
  the PUT response's `profile` object now use the same snake_case keys.
  camelCase is no longer accepted or returned. Nothing else in the
  frontend or backend used the camelCase API keys.
- `accounts/tests.py` — updated the two existing profile tests to
  snake_case and added: a PUT with the exact payload the frontend sends
  persists the name, email and address on `User` and `UserProfile`, and a
  following GET returns them; a PUT without `email` (as `mapFormToApi`
  sends when the field is empty) keeps the existing email. Before the fix,
  the new tests failed with the name unchanged and no `first_name` key in
  the GET.

**How to verify:** Run `pytest accounts && ruff check . && ruff format
--check .`. To check manually: change the first name and postal code in
the Dashboard profile form, save, clear localStorage and reload — the
values should come back from the server.

## P1-17: Account restore accepted weak passwords that every other password flow rejects

**What was broken:** `AccountRestoreConfirmAPIView` only checked that
`new_password` was at least 8 characters long. Registration, password
change and password reset all run Django's `validate_password`, so the
restore link was the one place where a common or all-numeric password such
as `12345678` was accepted.

**Why it mattered to the customer:** Restoring a deleted account can set a
new password in the same step. That step bypassed the password rules the
rest of the site enforces, so an account could come back with a password
that is trivially guessable.

**Files changed:**
- `accounts/views.py` — `AccountRestoreConfirmAPIView` now calls
  `validate_password` on a non-empty `new_password` instead of the length
  check. Failures return 400 with `{"new_password": [<messages>]}`, the
  same shape the password reset confirm view returns. Restore without a
  password is unchanged. As in the reset view, the validators run without
  the user object.
- `accounts/tests.py` — added: a common password (`password123`) and an
  all-numeric password (`48151623`) are rejected with the validator
  messages and the account stays deactivated; a strong password restores
  the account and is set as the new password. The two rejection tests
  failed before the fix (200 instead of 400).

**API change:** the error for a too-short or otherwise invalid password
moves from `{"detail": "Password must be at least 8 characters."}` to
`{"new_password": [...]}`. Any client that shows `detail` for this
endpoint needs to read `new_password` instead.

**How to verify:** Run `pytest accounts && ruff check . && ruff format
--check .`. To check manually: POST a valid restore link with
`"new_password": "12345678"` to `/restore/confirm/` — it should return 400
and the account should stay deactivated.

## P1-19: No tests for the order cancel, return and admin refund flows

**What was missing:** `orders/tests.py` covered the model, the checkout
webhook, refund sync and template rendering, but nothing exercised the
endpoints and admin actions that decide who gets money back:
`MyOrdersAPIView`, `CancelOrderAPIView`, `RequestReturnAPIView` and the
admin actions `approve_return`, `mark_return_received`,
`issue_stripe_refund` and `reject_return`.

**Why it mattered:** These paths call `stripe.Refund.create` and enforce the
cancel window, the return window and the final-sale rules. A regression
there either refunds an order that should not be refunded or blocks a
customer who is entitled to one, and nothing would have flagged it.

**Files changed:**
- `orders/tests.py` — tests only, no application code changed.
  `stripe.Refund.create` is mocked everywhere; no test calls Stripe.
  - `MyOrdersAPITestCase` (3): another user's orders are never returned,
    newest first, unauthenticated is 401.
  - `CancelOrderAPITestCase` (10): inside the 24h window it creates the
    refund (payment intent, metadata, idempotency key), stores the refund
    id and status, marks the order canceled and sends both emails; outside
    the window it is refused and Stripe is not called. Also refused, with
    Stripe not called: someone else's order (404), unauthenticated (401),
    order not paid, return workflow already started, refund already
    exists, no payment intent. A Stripe error leaves the order paid, and a
    refund response without an id returns 502 and leaves it paid.
  - `RequestReturnAPITestCase` (12): accepted for a delivered standard
    order inside the 14-day window; refused for a final-sale item, a
    non-returnable hygiene item, a custom-size item, a custom-length item,
    no `delivered_at`, outside the window, an existing request and an
    unpaid order; someone else's order is 404 and unauthenticated is 401.
    The window counts from delivery, not from purchase.
  - `OrderAdminReturnActionsTestCase` (7): for `approve_return`,
    `mark_return_received`, `reject_return` and `issue_stripe_refund`, a
    mix of qualifying and non-qualifying orders is run through the action.
    Only qualifying orders change (status and timestamp), the rest are left
    untouched, and the success and "N order(s) skipped" messages report the
    exact counts. `issue_stripe_refund` also checks that Stripe is called
    only for qualifying orders, that a `pending` refund gives
    `refund_pending` and a `succeeded` one gives `refunded`, and that a
    Stripe error or a response without an id is counted as failed and
    leaves the order unchanged.

**Result:** All 32 new tests passed on the first run against the current
code, so no bug was found and none was fixed.

**Observation, not changed:** `RequestReturnAPIView` refuses items with
`custom_length_selected=True`, but `approve_return` and
`issue_stripe_refund` do not check that flag (they check `return_policy`
and the custom-size label). A custom-length order cannot reach "requested"
through the API today, so this is only reachable if the return status is
set by hand in the admin. It is not covered by a test.

**How to verify:** Run `pytest orders && ruff check . && ruff format
--check .`.

## P1-21: `tresse/forms.py` and `tresse/models.py` were dead code, and one raised on import
