# Post-audit fixes — September 2026

## P1-02 — First-order promo code never shown

**What was broken:** `Order.tsx` checked order history by calling
`/orders/my-orders/`, but the backend route (`orders/urls.py`) is
`/orders/my/`. The request 404s, the catch block sets
`isFirstOrder(false)`, and the "15% off your first order" block with the
`TRESSE15` code never renders.

**Why it mattered to the customer:** The registration welcome email
promises new customers 15% off their first order with code `TRESSE15`,
but the order page never showed the promo, so first-time customers had
no way to see or use the discount they were told about.

**Files changed:**
- `src/view/Order.tsx`
- `src/view/Order.test.tsx`

**How to verify manually:**
1. Register a new account and open the order page before placing any
   paid order.
2. Confirm the "15% off your first order" block and `TRESSE15` code
   render.
3. Place and pay for an order, reload the order page, and confirm the
   promo block no longer renders.

## P0-11 — Session logged out ~30 minutes after login

**What was broken:** `refreshAccessToken` in `src/utils/axiosInstance.ts`
only read `resp.data.access` from `/accounts/token/refresh/`. The
backend has `ROTATE_REFRESH_TOKENS` and `BLACKLIST_AFTER_ROTATION`
enabled, so SimpleJWT returns a new access/refresh pair on every
refresh and blacklists the old refresh token. Since the frontend kept
reusing the now-blacklisted refresh token, the first refresh succeeded
and the second one failed, logging the user out.

**Why it mattered to the customer:** Sessions died roughly 30 minutes
after login regardless of activity, frequently interrupting customers
mid-checkout and forcing them to log in again to complete a purchase.

**Files changed:**
- `src/utils/axiosInstance.ts`

**How to verify manually:**
1. Log in.
2. Wait more than 30 minutes (long enough for at least one access
   token refresh cycle to occur).
3. Reload the page — the session must still be active, not logged out.

## P1-07 — Order history didn't show shipping/tracking info (frontend)

**What was broken:** `/orders/my/` now returns `tracking_number`,
`tracking_carrier`, and `shipped_at` on each order, but
`src/view/OrderHistory.tsx` didn't have those fields on its `Order`
type and never rendered them, so customers had no way to see when an
order shipped or track its package from the order history page.

**Why it mattered to the customer:** Customers had to contact support
to find out whether an order had shipped or to get a tracking number,
even though the backend already had that data.

**Files changed:**
- `src/view/OrderHistory.tsx`
- `src/view/OrderHistory.test.tsx`
- `styles/OrderHistory.css`

**How to verify manually:**
1. Open the order history page for an account with an order that has
   `tracking_number`, `tracking_carrier`, and `shipped_at` set.
2. Confirm a "Shipped" date renders next to the order's Date field.
3. Confirm a Tracking row renders with the carrier and tracking
   number, and that the number links to the carrier's tracking page
   (opens in a new tab).
4. Confirm an order without a tracking number shows neither the
   Tracking row nor a Shipped date.

## P1-03 — Wishlist toggle on the product detail page did nothing

**What was broken:** `ProductDetails.tsx` posted to
`/products/${product.id}/toggle_wishlist/`, a route that doesn't exist.
`ProductViewSet` defines the action as `url_path="wishlist"`, accepting
POST to add and DELETE to remove — the path `ProductCatalog.tsx` and
`WishList.tsx` already use correctly. The request 404s, the error is
swallowed into `console.error`, and the button silently does nothing.

**Why it mattered to the customer:** Clicking "Add to wishlist" (or
"Remove from wishlist") on a product's detail page appeared to do
nothing — no error was shown, and the product was never actually added
to or removed from the wishlist.

**Files changed:**
- `src/view/ProductDetails.tsx`
- `src/view/ProductDetails.test.tsx`

**How to verify manually:**
1. Log in and open a product's detail page.
2. Click "Add to wishlist" and confirm the button switches to "Remove
   from wishlist" and the product appears on the Wishlist page.
3. Click "Remove from wishlist" and confirm it switches back and the
   product is removed from the Wishlist page.

## P1-01 — "NOTIFY ME" in the product modal never subscribed anyone

**What was broken:** `ProductModal.handleNotifyMe` (`src/components/
ProductModal.tsx`) was a UI-only stub: it set `notifyDone(true)` and
returned, with a comment saying no API call existed yet. The button
showed "SUBSCRIBED" and reset after 2.5s no matter what, but
`POST /products/{id}/subscribe_back_in_stock/` was never called —
`ProductCatalog.tsx` already calls this endpoint correctly from its own
notify flow, but the modal (used from the Wishlist page's "ADD TO CART"
button, on out-of-stock products) didn't.

**Why it mattered to the customer:** A user clicked "NOTIFY ME" on an
out-of-stock item, saw "SUBSCRIBED", and left believing they'd get an
email when it restocked — no subscription was ever created, and no
email would ever arrive.

**Files changed:**
- `src/components/ProductModal.tsx` — `handleNotifyMe` now POSTs to
  `/products/{product.id}/subscribe_back_in_stock/` with no request
  body: this modal is only reachable while authenticated (via the
  Wishlist page), so the backend takes the subscriber's email from
  their account, matching how `ProductCatalog.tsx` skips the email
  field for authenticated users. Unlike `ProductCatalog.tsx`, this modal
  has no email input for guests, so an unauthenticated `handleNotifyMe`
  now no-ops instead of sending an unidentifiable request — consistent
  with `ProductCatalog`'s own guard against subscribing with no email.
  A failed request now sets a `notifyError` state (button reads "TRY
  AGAIN", resets after the same 2500ms) instead of showing "SUBSCRIBED"
  regardless of outcome.
- `src/view/WishList.test.tsx` — added a test that clicking "NOTIFY ME"
  on an out-of-stock product (as an authenticated user) posts to
  `/products/1/subscribe_back_in_stock/` and shows "SUBSCRIBED", and a
  test that a failed request shows "TRY AGAIN" and never "SUBSCRIBED".

**How to verify manually:**
1. Log in, open the Wishlist page with an out-of-stock item on it, and
   click "ADD TO CART" to open the product modal.
2. Click "NOTIFY ME" and confirm a request to
   `/products/{id}/subscribe_back_in_stock/` is sent and the button
   reads "SUBSCRIBED" for 2.5s.
3. With the backend unreachable (or the endpoint returning an error),
   click "NOTIFY ME" again and confirm the button reads "TRY AGAIN"
   instead of "SUBSCRIBED".

## P1-22 — Wishlist cards didn't show out-of-stock items as unavailable

**What was broken:** `WishList.tsx` rendered every card with an
always-enabled "ADD TO CART" button and no stock check at all, unlike
`ProductCatalog.tsx`, which shows an "OUT OF STOCK" badge and swaps the
action button based on `!product.available || !product.in_stock`.
Clicking "ADD TO CART" on a sold-out wishlist item opened `ProductModal`,
which does show "Out of stock" — but only after the customer had already
opened it, with nothing on the card itself hinting the item was
unavailable.

**Why it mattered to the customer:** Browsing the wishlist gave no visual
signal that an item was sold out; every card looked equally purchasable
until the customer clicked in and hit a dead end inside the modal.

**Files changed:**
- `src/view/WishList.tsx` — computes the same `isOut = !product.available
  || !product.in_stock` condition `ProductCatalog.tsx` uses, renders an
  "OUT OF STOCK" badge on the card (same text as the catalog badge) when
  true, and disables the "ADD TO CART" button for those products.
- `styles/WishList.css` — added `.wishlist__badge`, reusing
  `.catalog__badge`'s visual language (position, padding, translucent
  white background, uppercase letter-spacing). The existing
  `.wishlist__addBtn:disabled` rule already covered the disabled button
  state, so no button styling changed.
- `src/view/WishList.test.tsx` — added tests: an out-of-stock product
  renders the "OUT OF STOCK" badge and a disabled "ADD TO CART" button;
  an in-stock product renders neither the badge nor a disabled button.

**How to verify:** Run `npx tsc --noEmit && npm run test:run --
src/view/WishList.test.tsx`. To check manually, add an out-of-stock
product to the wishlist and confirm its card shows the "OUT OF STOCK"
badge with a disabled "ADD TO CART" button, while an in-stock item's
card looks unchanged.

## P0-06 — Newsletter unsubscribe link led nowhere (frontend)

**What was broken:** The backend added a signed-token unsubscribe
endpoint (`POST /newsletter/unsubscribe/<token>/`) and newsletter
welcome emails link to `/newsletter/unsubscribe/<token>/` on the
frontend, but no such route existed. Clicking the unsubscribe link in
an email hit the app's catch-all and landed the customer nowhere.

**Why it mattered to the customer:** Every newsletter welcome email
promises a working unsubscribe link; a customer who clicked it to opt
out had no way to do so, and had no path back to resubscribing if they
changed their mind.

**Files changed:**
- `src/view/NewsletterUnsubscribe.tsx` — new page component. On mount
  it reads `:token` from the URL and posts to
  `/newsletter/unsubscribe/<token>/`, rendering three states: an
  in-progress message, a success message (with the unsubscribed email)
  offering a "Resubscribe" button and a link back to `/catalog`, or a
  failure message showing the server's `detail` text. A missing/empty
  token short-circuits to the failure state without calling the
  endpoint. "Resubscribe" reuses the existing `subscribeNewsletter`
  helper against `/newsletter/subscribe/`.
- `src/App.tsx` — registered `/newsletter/unsubscribe/:token` as a
  public route (no `PrivateRoute`), alongside `/catalog` and `/cart`.
- `src/utils/newsletter.ts` — added `"unsubscribe"` to the
  `SubscribeSource` union so the resubscribe call can identify its
  origin, matching the existing `"modal"`/`"footer"` sources.
- `styles/NewsletterUnsubscribe.css` — new stylesheet for the
  page-specific state/action elements (spinner, resubscribe button,
  error text), layered on top of the existing shared `.policy` classes
  from `styles/Policy.css` (unchanged) so the page matches the other
  policy pages' typography, spacing, and muted palette.
- `src/view/NewsletterUnsubscribe.test.tsx` — added tests covering the
  in-progress, success, and failure states, and the resubscribe action
  (successful resubscribe shows a confirmation and hides the button;
  a failed resubscribe shows an error and keeps the button).

**How to verify:** Run `npx tsc --noEmit && npm run test:run`. To
check manually, subscribe to the newsletter, copy the unsubscribe link
from the welcome email, and open it: confirm it shows the in-progress
state briefly, then the success state with a "Resubscribe" button;
click "Resubscribe" and confirm it shows a confirmation instead. Open
the link again after it's already been used (or with a tampered token)
and confirm the failure state shows a message instead of a blank page.
