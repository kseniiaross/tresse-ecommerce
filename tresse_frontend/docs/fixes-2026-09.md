## P1-02 — First-order promo code never shown

**What was broken:** `Order.tsx` checked order history by calling
`/orders/my-orders/`, but the backend route (`orders/urls.py`) is
`/orders/my/`. The request 404s, the catch block sets
`isFirstOrder(false)`, and the "15% off your first order" block with the
`TRESSE15` code never renders.

**Why it mattered to the customer:** The registration welcome email
promises new customers 15% off their first order with code `TRESSE15`,
but the order page never showed the promo, so first-time customers had
no way to see or use the discount they were told about.

**Files changed:**

- `src/view/Order.test.tsx`

**How to verify manually:**

   paid order.

   render.

   promo block no longer renders.

## P0-11 — Session logged out ~30 minutes after login

**What was broken:** `refreshAccessToken` in `src/utils/axiosInstance.ts`
only read `resp.data.access` from `/accounts/token/refresh/`. The
backend has `ROTATE_REFRESH_TOKENS` and `BLACKLIST_AFTER_ROTATION`
enabled, so SimpleJWT returns a new access/refresh pair on every
refresh and blacklists the old refresh token. Since the frontend kept
reusing the now-blacklisted refresh token, the first refresh succeeded
and the second one failed, logging the user out.

**Why it mattered to the customer:** Sessions died roughly 30 minutes
after login regardless of activity, frequently interrupting customers
mid-checkout and forcing them to log in again to complete a purchase.

**Files changed:**
- `src/utils/axiosInstance.ts`

**How to verify manually:**
1. Log in.
2. Wait more than 30 minutes (long enough for at least one access
   token refresh cycle to occur).
3. Reload the page — the session must still be active, not logged out.

## P0-07 — Meta and TikTok pixels fired before cookie consent

**What was broken:** `index.html` ran the Meta Pixel and TikTok Pixel
bootstrap snippets synchronously on page load — `fbq("init", ...)`,
`fbq("track", "PageView")`, `ttq.load()`, and `ttq.page()` — plus a
Facebook `<noscript>` image pixel, all before React even mounted and
regardless of any cookie choice. `metaPixel.ts` and `tiktokPixel.ts`
only checked that `window.fbq` / `window.ttq` existed, never the saved
consent, so `trackTikTok("InitiateCheckout")` in `Order.tsx` and
`trackTikTok("Purchase")` in `OrderSuccess.tsx` fired even for a
visitor who had pressed "Reject Optional". `cookiePreferences.ts`
already saved the choice and dispatched
`"tresse:cookieConsentUpdated"`, but nothing listened for it.

**Why it mattered to the customer:** The cookie banner and the Privacy
Policy both promise that optional marketing technologies run only when
enabled. In reality, Meta and TikTok tracked every visitor's page views
and purchases regardless of their choice — a real gap between the
stated policy and actual behavior, and a compliance risk.

**Files changed:**
- `index.html` — removed both inline pixel bootstrap `<script>` blocks
  and the Facebook `<noscript>` image. The
  `facebook-domain-verification` `<meta>` tag is unchanged.
- `src/utils/pixelLoader.ts` — new module. `initMarketingPixels()`
  checks `getCookieConsent()?.marketing`; when granted it dynamically
  injects the Meta (`fbevents.js`) and TikTok (`events.js`) scripts —
  each guarded by a loaded flag and a `document.getElementById` check
  so a script is never injected twice — initialises them with the same
  pixel ids index.html used (`4422176017804002` / `D8QLFQJC77UDQUH99PN0`),
  and fires the initial `fbq("track", "PageView")` / `ttq.page()`. It
  also attaches a one-time listener for `"tresse:cookieConsentUpdated"`
  that re-evaluates consent: loads the scripts if newly granted, or (if
  they'd already loaded) calls `fbq("consent", "revoke")` and
  `ttq.revokeConsent()` if consent is later withdrawn.
- `src/App.tsx` — calls `initMarketingPixels()` once in a `useEffect`
  on mount, covering both returning visitors who already consented and
  the in-session consent-change case (via the listener the loader
  attaches internally).
- `src/utils/metaPixel.ts`, `src/utils/tiktokPixel.ts` — `trackMeta`
  and `trackTikTok` now return early unless
  `getCookieConsent()?.marketing` is true, so every existing call site
  (`ProductDetails.tsx`, `ProductCatalog.tsx`, `Order.tsx`,
  `OrderSuccess.tsx`) is covered without being touched.
  `tiktokPixel.ts`'s `Window.ttq` type gained the extra fields
  (`revokeConsent`, `load`, `_i`/`_t`/`_o`/`_q`) the loader needs.
- `src/utils/pixelLoader.test.ts`, `src/utils/metaPixel.test.ts`,
  `src/utils/tiktokPixel.test.ts` — new tests: the tracking helpers no-op
  without marketing consent and call through with it; the loader
  injects no script without consent, injects each script exactly once
  with consent (including on a repeated `initMarketingPixels()` call),
  does not inject again on a second `"tresse:cookieConsentUpdated"`
  event, and calls the vendor revoke APIs when consent is withdrawn
  after loading (but not when it never loaded).

**How to verify:** Run `npx tsc --noEmit && npm run test:run && npm run
lint`. To check manually: open the site in a fresh session, reject
optional cookies, and confirm the Network tab shows no request to
`connect.facebook.net` or `analytics.tiktok.com`. Accept marketing
cookies (or reopen Cookie Settings and enable it) and confirm both
scripts load exactly once and a `PageView`/`page()` call fires. Reject
again afterwards and confirm no new script loads and no further
tracked events fire.

## P1-14 — Cookie Settings modal couldn't be closed from the keyboard

**What was broken:** `CookieSettingsModal.tsx` — the first dialog every
new visitor sees — had none of the standard dialog behavior that
`CustomMeasurementsModal.tsx` already gets from the shared
`useDialogDismiss` hook: no Escape-to-close, no focus moved into the
dialog on open, no focus restored on close, no overlay-click close, and
no body scroll lock. The monkey-test log confirmed the practical
impact: after opening "Cookie Settings", three consecutive clicks
timed out because the overlay swallowed them, and the modal only went
away on a forced navigation. The clickable overlay also carried
`role="presentation"`, which misrepresents an element that closes the
dialog on click.

**Why it mattered to the customer:** A modal that only a mouse click
on its own close button can dismiss is a dead end for keyboard and
assistive-tech users, and a visitor who instinctively clicks the
darkened backdrop or presses Escape — the two most common ways people
try to back out of a dialog — gets stuck on the very first screen of
the site.

**Files changed:**
- `src/components/cookies/CookieSettingsModal.tsx` — wired up
  `useDialogDismiss` the same way `CustomMeasurementsModal.tsx` does:
  `overlayRef`/`contentRef` refs, `tabIndex={-1}` on the dialog
  `<section>` so it can receive focus, `onClose` passed through. The
  component is only mounted while open, so the hook's default
  `active=true` is correct (no `open` prop to pass). Removed
  `role="presentation"` from the overlay `<div>`. Added the same body
  scroll lock `CustomMeasurementsModal.tsx` uses (sets
  `document.body.style.overflow = "hidden"` while mounted, restores the
  previous value on unmount). Consent logic, saved preferences, and
  markup/classes (visual design) are unchanged.
- `src/components/cookies/CookieSettingsModal.test.tsx` — new tests:
  Escape calls `onClose`; a mousedown on the overlay calls `onClose`; a
  mousedown inside the dialog does not; focus moves into the dialog on
  open; Save calls `onSave` with the chosen preferences (both when
  checkboxes are toggled and when left at their initial values).

**How to verify:** Run `npx tsc --noEmit && npm run test:run && npm run
lint`. To check manually: clear site data, reload, and open "Cookie
Settings" from the banner. Press Escape and confirm it closes; reopen
and click the darkened backdrop (not the dialog itself) and confirm it
closes; reopen and confirm keyboard focus starts inside the dialog;
confirm the page behind the modal doesn't scroll while it's open;
change a preference and click "Save Preferences" and confirm the
choice is saved as before.

## P1-15 — Modals didn't trap keyboard focus

**What was broken:** `useDialogDismiss.ts` moved focus into a dialog on
open, restored it on close, and closed on Escape or an overlay click —
but never trapped Tab/Shift+Tab. Pressing Tab from the last control in
any modal moved focus onto the page underneath, which is visually
hidden behind the fixed overlay but still focusable, letting a keyboard
user keep tabbing (and typing) into content they can't see. Every modal
on the site uses this hook — `NotifyModal`, `SizeModal`, and
`CustomLengthModal` in `ProductCatalog.tsx`, plus `ProductModal`,
`CustomMeasurementsModal`, and `CookieSettingsModal` — so the gap was
site-wide. A correct Tab/Shift+Tab trap already existed, but only for
the one-off newsletter modal in `Home.tsx`
(`getModalFocusableElements` and the `Tab` branch of its own keydown
handler), instead of the shared hook every other modal relies on.

**Why it mattered to the customer:** A keyboard-only or screen-reader
user tabbing through any modal — including the very first thing a new
visitor sees if they open Cookie Settings — could tab straight out of
the dialog and into invisible page content, losing track of where
focus was and effectively getting stuck.

**Files changed:**
- `src/hooks/useDialogDismiss.ts` — added Tab/Shift+Tab handling to the
  existing `keydown` listener, scoped to `contentRef.current`: collects
  focusable descendants matching `a[href]`, non-disabled
  `button`/`input`/`select`/`textarea`, and `[tabindex]` other than
  `-1`; Tab on the last one wraps to the first, Shift+Tab on the first
  wraps to the last; Tab/Shift+Tab while focus is on the dialog
  container itself (its initial focus target) moves to the first/last
  descendant respectively; with no focusable descendants, focus stays
  on the container. Only runs while the hook is `active`. Escape,
  overlay-click close, initial focus-in, and focus-restore on close are
  unchanged. `Home.tsx`'s own newsletter-modal focus trap was left
  as-is (out of scope for this fix).
- `src/hooks/useDialogDismiss.test.tsx` — new tests: Tab from the last
  control wraps to the first; Shift+Tab from the first wraps to the
  last; Tab/Shift+Tab from the container itself goes to the
  first/last; a middle control is left alone; no focusable descendants
  keeps focus on the container; and the pre-existing Escape,
  overlay-close, no-close-from-inside, focus-in, and focus-restore
  behavior all still pass unchanged.

**How to verify:** Run `npx tsc --noEmit && npm run test:run && npm run
lint`. To check manually: open any modal (e.g. Cookie Settings, a
product's size selector, or the "Notify Me" modal), tab to its last
control, press Tab again, and confirm focus wraps to the modal's first
control instead of landing on the page behind it; press Shift+Tab from
the first control and confirm it wraps to the last.

## P1-10 — Guest cart couldn't tell apart two lines of the same product+size

**What was broken:** `addToCart` in `cartSlice.ts` correctly creates a
separate line for each distinct set of custom measurements/custom
length (`sameMeasurements`/`sameCustomLength`), but `removeFromCart`,
`updateQuantity`, `updateCustomMeasurements`, and `setItemMaxQty` all
looked up a line by `id + product_size_id` only — which two such lines
share. A customer who added the same sweater twice with different
measurements (say 90/70/95 and 95/75/100) got two lines as intended,
but pressing "Remove" on the second deleted both (the filter matched
both by id+product_size_id), and pressing "+"/"−" or editing
measurements on the second silently acted on whichever line
`Array.prototype.find` happened to return first — usually the first
one added, not the one the customer was looking at.

**Why it mattered to the customer:** Anyone customizing the same
product twice with different measurements — a common flow for
made-to-order swimwear/knitwear — could delete the wrong line entirely
or edit the wrong line's quantity/measurements without any visible
error, silently corrupting their order before checkout.

**Files changed:**
- `src/utils/cartSlice.ts` — every `GuestCartItem` now carries a
  stable `lineId: string`, generated in `addToCart` when a new line is
  created (`crypto.randomUUID()`, with a `line_<timestamp>_<random>`
  fallback for environments without it). `loadFromLS` now backfills a
  `lineId` onto any stored line that predates this field and persists
  the backfilled cart immediately, so carts saved before this change
  keep working. `removeFromCart`, `updateQuantity`,
  `updateCustomMeasurements`, and `setItemMaxQty` now all address a
  line by `lineId` instead of `id + product_size_id`.
- `src/types/cart.ts` — added `lineId: string` to the (separately
  hand-maintained) `GuestCartItem` type used by `Cart.tsx`.
- `src/view/Cart.tsx` — `handleQuantityChange` and `handleRemove` now
  take a `guestLineId` instead of `guestProductSizeId`; the guest cart
  list's React `key`, its "Remove" button, its quantity `−`/input/`+`
  handlers, and `handleSaveMeasurements`'s `updateCustomMeasurements`
  dispatch all now pass `item.lineId`. The server cart path (keyed by
  its own server item id) is unchanged.
- `src/utils/cartSlice.test.ts` — updated the existing
  `removeFromCart`/`updateQuantity`/`updateCustomMeasurements`/
  `setItemMaxQty` tests to dispatch by `lineId`, and added: two lines
  for the same product+size with different measurements — removing the
  second leaves the first untouched; updating the quantity of the
  second leaves the first untouched; updating the measurements of the
  second leaves the first untouched; a line loaded from storage without
  a `lineId` receives one (and it's persisted back to storage); an
  existing stored `lineId` is left as-is; `addToCart` assigns distinct
  `lineId`s to distinct lines.
- `src/view/Cart.test.tsx` — `makeGuestItem()`'s fixture now includes a
  `lineId`, since the "Remove" button and quantity controls need one to
  find their line (the existing "removes a guest item when Remove is
  clicked" test would otherwise silently stop removing anything).

**How to verify:** Run `npx tsc --noEmit && npm run test:run && npm run
lint`. To check manually: as a guest, add the same product/size to the
cart twice with two different sets of custom measurements so you get
two separate cart lines, then click "Remove" on the second line and
confirm only that line disappears; separately, change the quantity or
edit the measurements on the second line and confirm the first line's
quantity/measurements are unaffected.

## P1-12 — Failed guest-cart merge line got re-posted and doubled on retry

**What was broken:** `mergeGuestCart` in `serverCartSlice.ts` posted
every guest cart line with `Promise.allSettled` and cleared the whole
guest cart only if every request succeeded. If one line succeeded and
another failed (a stock check, a transient network error), the entire
guest cart was kept — including the line that had already been
transferred to the server. On the customer's next login the merge ran
again, posting that already-transferred line a second time; the
backend's `CartItemAPIView` adds the incoming quantity onto the
existing server item rather than rejecting the duplicate, so the
customer ended up with two of that item instead of one. The test "does
not clear guest cart if any request fails" pinned this as the intended
behavior.

**Why it mattered to the customer:** Any guest who added several items,
hit one transient failure while merging at login, and logged in again
later would silently see one of their items duplicated in the cart —
with no error or indication anything had gone wrong.

**Files changed:**
- `src/store/serverCartSlice.ts` — `mergeGuestCart` now removes each
  guest line from the guest cart as soon as its own request succeeds
  (`dispatch(removeFromCart({ lineId: it.lineId }))`, using the
  `lineId` added in the previous change), instead of waiting for every
  request to settle and clearing the whole cart in bulk. Requests still
  run concurrently via `Promise.allSettled`; a line whose request fails
  is simply left in the guest cart for the next merge attempt, and a
  failure is still logged via `console.warn`.
- `src/store/serverCartSlice.test.ts` — `makeGuestItem()`'s fixture now
  includes a `lineId` (auto-incrementing per call, like the guest cart
  test fixtures already do). Replaced "does not clear guest cart if any
  request fails" — which pinned the old, now-incorrect behavior — with
  two tests: after a partial failure only the failed line remains in
  the guest cart; and a second merge attempt posts only that
  previously-failed line (and the guest cart ends up empty once it
  succeeds).

**How to verify:** Run `npx tsc --noEmit && npm run test:run && npm run
lint`. To check manually: as a guest, add two different items to the
cart, then (e.g. via dev tools) make one item's add-to-server-cart
request fail while logging in so the merge partially fails. Confirm
only the failed item remains in the guest cart, and log in again (or
retrigger the merge) to confirm just that item is posted and the guest
cart ends up empty with no duplicated quantities on the server cart.

## P1-13 — A failed post-registration fetchCart showed "Registration failed"

**What was broken:** `Register.tsx` awaited
`dispatch(mergeGuestCart()).unwrap()` and
`dispatch(fetchCart()).unwrap()` back to back with no try/catch of
their own. If `fetchCart` failed (a transient network error, a slow
backend), the exception reached the outer `catch`, which set
`serverError` to "Registration failed. Please try again." — even
though `registerUser` had already succeeded, the account existed, and
`setCredentials` had already logged the user in. Retrying registration
then failed with "User with this email already exists.", leaving the
customer stuck believing registration never worked.
`Authorization.tsx` already wraps the same two calls in their own
individual, non-blocking `try/catch` blocks (logging via
`console.warn` in dev, never blocking the login flow) for exactly this
reason — the fix in `Register.tsx` had just never been applied there.

**Why it mattered to the customer:** A brand-new customer who hit a
transient error immediately after registering was shown a false
failure message for an account that already existed and was already
logged in, then got a second, contradictory error ("already exists")
on retry — with no way to tell from the UI that they could just
navigate away and were, in fact, already signed in.

**Files changed:**
- `src/components/Register.tsx` — wrapped
  `await dispatch(mergeGuestCart()).unwrap()` and
  `await dispatch(fetchCart()).unwrap()` in their own `try/catch`
  blocks, matching `Authorization.tsx` exactly: a failure of either is
  logged with `console.warn` in dev and otherwise ignored: it no

## P1-05 / P1-06 — Return button counted from the wrong date and did nothing

**What was broken:** Two problems in the return flow on the order
history page (`src/view/OrderHistory.tsx`).
- **P1-05:** `isReturnable` showed the Return button while
  `now - created_at <= 14 days`. The Return Policy and
  `RequestReturnAPIView` (`POST /orders/<id>/return/`) count the 14 days
  from delivery and reject orders without `delivered_at`. Production
  takes 1–2 weeks plus transit, so the button vanished before the parcel
  arrived and was shown for orders the backend would refuse.
- **P1-06:** the button called `goToReturns`, which navigated to
  `/help?topic=return&order=...`. `Help.tsx` never reads those params, so
  the customer landed on the generic help page and the return endpoint
  was never called.

**Why it mattered to the customer:** A customer whose order arrived on
day 10 had no Return button at all, and one who did see it was sent to a
help page that couldn't start a return.

**Files changed:**
- `src/view/OrderHistory.tsx` — `isReturnable` now uses `delivered_at`:
  hidden when it is empty or unparseable, shown while
  `now - delivered_at <= 14 days`. It is also hidden once the order has a
  `return_status`, since the backend rejects a second request and the
  button would otherwise stay on screen after success. The Return button
  now asks for confirmation (`window.confirm`), POSTs to
  `/orders/<id>/return/`, replaces the order in the list with the
  response (same approach as cancel) and shows a "Return: Requested"
  field on the card. On failure it shows the server's `detail` (e.g.
  "Return window has expired", "Custom-sized items are final sale."),
  falling back to a generic message if there isn't one. Removed
  `goToReturns` and the `useNavigate` import. Cancel logic is untouched;
  the return uses its own `returningId` state so the Cancel button label
  doesn't change while a return is in flight.
- `src/view/OrderHistory.test.tsx` — replaced the created_at-based
  window tests and the navigation test. New tests cover: shown within 14
  days of delivery and on day 14; hidden without `delivered_at` and after
  14 days from it (even for a just-placed order); hidden once a return
  exists; declining the confirm posts nothing; confirming posts to
  `/orders/1/return/` and shows the return status in place; a rejection
  shows the server's message; a non-server failure shows the generic
  message.

**How to verify:** Run `npx tsc --noEmit && npm run test:run && npm run
lint`. To check manually: with a paid order that has `delivered_at` set
within the last 14 days, open My Orders, click Return and confirm — the
card should show "Return: Requested" and the button should disappear.
With `delivered_at` empty or older than 14 days, no Return button
appears. Requesting a return on an order containing a final-sale item
should show the backend's message.
